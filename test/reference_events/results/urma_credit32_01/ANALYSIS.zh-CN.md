# 软件准入8→32：无完整Dispatch净收益，关闭扩窗方向

结果提交83717e2f。四项、两端共8份status均通过；实际窗口8/32、设备202c1/204c0、202全开/204 tail-off、ordered回收与计划一致。开发侧从原始api_samples独立复算，上传summary的per_node、paired_calls、rounds、decision逐字段一致。源码/模块/boot/库、固定负载及无采集batch节奏通过汇总工具校验。

## 如何收敛

1. 保留窗口8，关闭当前简单扩窗方向，不追加16/64扫描或更换节点继续试。
2. 原FIFO重放中“队头完成推进迟→窗口满→后续命令读取晚”的事实仍成立，但这组因果干预没有证明提高准入能消除主要净耗时。满额不能直接等同错误配置或可回收的完整API损失。
3. 结果也不能单独证明硬件慢、provider慢或所有软件调度都无效。更高并发可能把等待移入设备队列，当前未采阶段数据，不声称已测得这种迁移。
4. 下一步候选应从真实后端差异挑选，优先保留持续混合负载下的顺序/完成推进与GPU访问路径；额外quiet交互是已确认的实现差异，但还没有时延贡献证据，不直接删减。
