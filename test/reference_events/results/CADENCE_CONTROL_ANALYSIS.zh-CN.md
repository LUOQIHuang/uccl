# 采样方式对照：关闭采集仍复现204 BF16约16%的局部计时下降

复核上传df600331：urma_ref_4096_batch_01、urma_ref_4096_paced_01，两端全部齐全。已独立重跑summarize_cadence.py，输出cadence_controls.csv与上传内容逐行完全一致。两组status均rc=0、所有checks为True；严格身份及同模块SHA检查通过，5次预热/10次采样，丢首样本后9个有效值。

两组都没有开启GPU/CPU事件和主机时钟，reference_control执行标记正确，也没有event_trace.jsonl。它们的区别是连续调用与逐样本同步/barrier/Event创建这一组采样方式。

204 BF16的batch有效样本为7919.104–8073.984μs，paced为6616.064–6904.064μs；全部9个paced样本均低于全部batch样本，不能解释成单个离群值。各组CV均低于1.35%。Combine控制项约+1.69%～+1.99%，layout约+0.55%/+1.70%，没有相同的16%下降。

**关闭采集时也能复现此前on的204 BF16下降，说明采样方式本身已足以触发该现象。它不是GPU事件记录或时钟线程必然产生的效果。**但本轮未逐个拆开barrier、同步和Event创建，不能进一步声称其中某一个调用已被单独证明是原因。

## 为什么不代表双机任务加速16%

这是204本地CUDA Event计时窗口的变化。202 BF16同时从7979.833升到8113.949μs；两端均值中较大者为7984.839→8113.949μs，反而约+1.62%。该值也不是共同起点下完整双机端到端计时，只用于避免把一个节点的局部窗口下降误读成整体加速。

一种解释是同步改变了两端发起、排队及等待的相对位置，使204计时区间内承担的等待减少；这是推测，当前没有共同跨节点时间基准证明具体哪段等待被移动。可以确定的是kernel/模块没有更换、没有采集活动，测量方式改变了实际执行条件。

生产源码、模块、SDK/库、设备、boot及形状一致，归一化身份只有diagnostics版本不同；旧on在新增batch/paced入口前采集，故这张表只是跨轮线索，不能冒充严格同脚本版本验收。202 FP8旧on的8.846ms离群值仍保留，不能删除后宣布全部通过。

这表明原来的−15.64%主要是将不同采样方式直接比较所产生的局部计时变化；不能继续据它否定所有阶段记录，也不能将其当作URMA优化。已有GPU三个事件和CPU逐请求链仍是逐样本执行形态下的观察；它们并未覆盖最终Receiver完成，也没有对应verbs事件，原始URMA/verbs性能差额仍未得到最终归因。

## 下一步最小闭环

不再重跑batch/paced/off/base/post，只补**同一当前脚本版本的on**一个任务，用本次paced作为匹配控制，以便严格检查开启采集的净变化与原始阶段记录。模块继续复用，操作见[匹配采样方式运行文档](../MATCHED_TRACE.zh-CN.md)。这一步不修改GPU或测量入口，只新增离线分析器及文档；不会因诊断脚本哈希变化而要求重做paced。

通过后，后续URMA/verbs阶段对比统一paced/on口径，连续调用的原benchmark基线仍单独保留，不混为一种工作负载。另一后端只在其可用内核窗口运行同口径采集，不要求现在切核，也不继续增加URMA测量方式扫描。
