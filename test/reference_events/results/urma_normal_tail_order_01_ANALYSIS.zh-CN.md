## 交替提交只覆盖少数请求

每端 9 个有效 BF16 trace 窗口，每窗匹配 132 对，合计 1188 对。匹配条件为同 Proxy、同设备队列、同 ring 的连续请求 ID，且 payload 字节数等于通知 token 数乘 14352。根据同 Proxy 连续的 `prepare` 记录重建收集批次，再按 SDK 链的 `post_begin/post_end` 判断实际位置。

| 发送端 | 匹配 WRITE/FADD | 同一 Proxy 批且标记配对 | FADD 在同一 SDK 链里确实排到后续 WRITE 前 |
| --- | ---: | ---: | ---: |
| 202 | 1188 | 100（8.42%） | 56（4.71%） |
| 204 | 1188 | 114（9.60%） | 12（1.01%） |

同批数与配对标记数逐窗一致。**本轮约九成对应 WRITE/FADD 在不同 Proxy 收集批中出现**，因此原位调整触及的范围有限。即使同批，后面还必须有同队列 WRITE，交替才会改变链内先后位置。微基准则预先把每队列四对都凑进同一批，因此有更多可提前的机会。采集阶段的覆盖率仅用于描述记录到的 BF16 窗口，未直接量到无采集时的批次分布。[逐窗链内移动统计](urma_normal_tail_order_01_trace_summary/visibility_windows.csv)

## 接收侧未见可信的消费提前

202 的 trace 通过该端代表性检查，最早可消费的远端 token 中位从 864.59 μs 到 883.19 μs，最后一个从 7532.00 μs 到 7508.33 μs，各自以本地首个发送 token 为时间基准。两个变化都小于采样时钟最大间隙约 69–91 μs，不能把这两个差值作为已验证的 GPU 收益。204 的 A、B trace CV 分别为 20.92% 和 12.52%，双端 trace 代表性门槛因此未通过。链位置的直接观测依然可以用来审查开关覆盖。[采集控制](urma_normal_tail_order_01_trace_summary/trace_controls.csv)

本轮否定的是**这版只重排同批已匹配请求的策略能在完整 Normal 取得稳定收益**。微基准已验证链内顺序可推迟前部通知，但生产 Proxy 很少把对应请求收进同一批，当前结果尚未测量跨批次配对策略的收益。若以后考虑跨批次合并，需要单独衡量等配对的时间及背压，并验证正确性。此前在 204 观察到的返回值已可读后仍约 285 μs 的完成交付等待，仍是可单独继续核查的区间。[密集 FADD 采样](../../fadd_path/results/fadd_dense_01/ANALYSIS.zh-CN.md)
