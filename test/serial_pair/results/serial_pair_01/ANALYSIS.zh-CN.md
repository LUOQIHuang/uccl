# URMA最小串行首轮：没有复现数百微秒的WRITE/FADD完成观测分离

输入提交`8d524016`，目前只有URMA后端。开发端重新执行analyze.py，核查两端状态、原始逐对时间戳与配置，分析成功；verbs的本轮串行对照尚未上传。

## 1. 实验是否真正执行了单队列串行

两端status均passed=true、correctness=true，driver rc=0，各完成12个点（4种方向/数据量×3轮）。两端overlay完全一致。

| 核查项 | 实际记录 |
| --- | --- |
| 工作线程及CPU | 每端一个调用线程；202固定CPU168，204固定CPU192，GPU NUMA均为2 |
| 活跃数据队列 | channels=1；Normal另有独立控制端点，本轮不承载数据 |
| 路径 | 生产UrmaTransport，源payload和远端通知计数器均GPU内存 |
| 顺序与完成 | WRITE RELAX、FADD STRONG＋per_request fence、completion all |
| WRITE/FADD | WRITE459264B；FADD向远端计数器加32 |
| 在途限制 | 每对两条完成全部取得后才提交下一对；分析逐请求验证此条件 |
| 32/64含义 | 每迭代单向发送1/2对；64的两个存储槽用于分别校验，不是窗口2 |
| 测量之外 | TCP同步、GPU逐字节payload与计数器检查、JSON输出 |

没有关闭fence来取得本轮结果，也没有把FADD改成主机模拟。

## 2. 具体结果

总SDK跨度取三轮迭代均值的中位数；单对分位数汇集三个有效轮次。每点每轮20次预热，101次计时丢首值后100个有效迭代。

| 数据量/方向 | 有效迭代 | 有效请求对 | 总SDK跨度 μs | 单对中位 μs | 单对P95 μs | W→A中位 μs |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 32，202→204 | 300 | 300 | 39.208 | 39.120 | 39.790 | 0 |
| 64，202→204 | 300 | 600 | 78.222 | 38.920 | 39.420 | 0 |
| 32，204→202 | 300 | 300 | 37.651 | 37.585 | 37.881 | 0 |
| 64，204→202 | 300 | 600 | 74.908 | 37.330 | 37.711 | 0 |

四点均通过原稳定性门槛，最大轮内CV为2.933%，轮均值跨度最高0.564%。32与64的总跨度大致为1:2，64内每对仍约37～39μs，没有出现第二对的显著积压。

两方向合计1800对有效请求（每端作为发送方900对）。原始记录核查：全部WRITE/FADD具有相同SDK poll序号和相同完成观测时间。0μs只表示两条完成在同一批查询返回，不能理解为atomic物理执行耗时为0。

WRITE和FADD的SDK提交中位耗时约0.72～0.93μs；此处URMA将两条请求链式提交，同一调用的两份记录不能相加。

## 3. 与原完整Normal观测有什么关系

| 发送端 | 原完整Normal第6块W→A中位 | 本轮单队列串行W→A |
| --- | ---: | ---: |
| 202 | 682.990μs | 0，同次SDK返回 |
| 204 | 427.350μs | 0，同次SDK返回 |

两组只用于判断能否复现同一种现象，不是仅改变一个因素的A/B，也不能计算“优化了100%”。本轮没有优化完整Normal。

明确得到的结论：

1. URMA在该最小环境下可以在约37～39μs完成一次459264B WRITE及其通知FADD。数百μs的W→A观测分离不是每对请求必然具有的固定成本。
2. 在本轮条件下，保留STRONG/fence仍能很快完成。因此不能将此前现象简化为“只要开fence就固定多等数百μs”。fence在有前序请求/资源竞争时的代价仍可能不同。
3. 原异常需要本轮未包含的某些条件，或条件组合：多队列/多个在途请求、原Proxy服务与回收、双向完整负载、GPU生产/消费和反馈，以及更大的注册区域/不同布局。
4. 本轮同时改变了这些因素，尤其从未固定绑核的完整Proxy改为GPU NUMA本地单核直接轮询；不能单独断言“通道多是根因”或“CPU绑核已解决Normal”。
5. 本轮测本端SDK完成，接收GPU在计时后做正确性检查，不是远端GPU首次可消费时延。实际atomic执行可能包含在整对37～39μs内。

## 4. 还不能得到的结论

- 尚无同口径verbs串行结果，不能判断URMA与verbs在最小环境下谁更快或快多少。
- 不能从0μs间隔推出设备无等待、provider没有问题，或完整Normal的背压不存在。
- 不能把原完整Normal的毫秒级API差距与本轮微基准相减，作为可取得的优化收益。
