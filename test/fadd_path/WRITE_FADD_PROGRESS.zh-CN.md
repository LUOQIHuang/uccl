# Normal WRITE/FADD 等待问题的实验与优化记录

整理日期为 2026-11-20。时延数据覆盖至 `33c5877e`，provider 能力及详细采集结果覆盖至 `ddcac8a6`。本文串联这条调查线上的完整 Normal、局部采样、隔离微基准和优化干预，链接指向保留原始数据的报告。

**已取得的优化证据是关闭 204 Normal 数据 FADD 的 fence，完整 BF16 Dispatch 在严格反向配对中平均缩短 277.52 μs（3.433%）。后续将改动缩到仅关闭 tail fence，最近四个关闭探针的运行均值为 7.813–7.892 ms，但全开基线发生轮间漂移，tail-only 的稳定收益百分比仍待确认。剩余重要观测是 204 的 FADD 返回值已可读后，仍需约 350 μs 才取得 SDK 完成记录。**

## 测量范围和事件含义

主线固定为 Normal BF16 Dispatch，每 rank 4096 tokens、hidden=7168、experts=256、top-k=8、SM=24、NVL chunk=4、RDMA chunk=32。202 为 rank0，204 为 rank1，两端都发送和接收。完整 Normal 每端有 4 个 Proxy。隔离微基准另列线程、队列和负载，单向微基准中的 32/64 tokens 是一次迭代的单向工作量。

以下事件都要区分。R 与 W 的实际先后可能随配置改变。

```text
发送 GPU 发布一批数据的 WRITE 和 tail FADD 命令
  → 发送端 Proxy 读取、准备、提交
  → W：发送端 SDK 返回 WRITE 的完成记录
  → R：发送端 CPU 读到对应 FADD 返回的旧计数值（本地返回槽）
  → A：发送端 SDK 返回 FADD 的完成记录
  → Proxy 回收请求额度，后续命令获得推进机会

接收 GPU 同时检查远端 tail 和数据状态，满足消费条件后继续。
接收 GPU 消费本批数据不以发送端 CPU 先读到 A 为前提。
```

本文的“完成”指本端软件观测。W→A 包括顺序依赖、设备排队与执行、响应、完成发布及软件发现。R 通过最后一次读到零和第一次读到非零给出时间界限。设备物理 CQE 发布时刻仍缺失。CQE 是设备写入完成队列的记录，SDK 轮询将其交给应用。

完整 Dispatch 净收益使用关闭探针的调用耗时。近期双端主指标是同序号调用先取两端本地耗时较大者，再对有效样本求均值。它没有统一跨机起止时刻。各请求重叠执行，逐请求中位数或累计等待均不能直接加到 Dispatch 上。每端 36 对通常来自 9 个窗口×4 个 Proxy，同一批请求不算 36 轮独立实验。

## 1. 从整体回退收窄到通信推进与通知完成

历史匹配组中，202 完整 BF16 Dispatch 从 verbs 的 **7.149 ms** 到 URMA 的 **8.114 ms**，增加 **965 μs（13.50%）**。204 为 **6.826→6.703 ms**，没有同方向回退。202 可能在等 204 的数据，因此两端都需要观测。

同一批采集窗口内，202 首 token→首次本地 WRITE 的跨度均值为 **0.401→0.422 ms**，差约 20 μs。首次本地 WRITE→本机最后一个远端 token 有效的双向推进包络为 **6.389→7.110 ms**，差约 721 μs。这支持进入持续通信阶段细查。该跨度包含多通道准备、提交、传输、通知及接收，和同一 WR 的网络时延有不同起止点。[整体与分段证据](../reference_events/results/normal_progress_20261116/README.zh-CN.md)

204 读到命令后，解码到准备、准备到提交、SDK 提交的中位数分别为 verbs **3.02、0.47、0.70 μs**，URMA **3.22、0.56、0.75 μs**。更明显的差异出现在提交后长尾，大 WRITE P95 为 **2.290→3.450 ms**。URMA 最慢 5% 的 60 条大 WRITE 中，59 条集中在每 ring 的第 6 块。

围绕该位置和末块补点，发现 URMA 末块命令发布后，CPU 仍晚 **1.922 ms（202）／3.578 ms（204）** 才读到。离线重放 FIFO 后，这段期间软件 pending=8 的占比中位为 **99.554%／99.662%**，满额且队首 ATOMIC 尚无完成观测为 **99.472%／99.590%**。由此获得可观测的传导链。

```text
通知原子请求尚无完成观测
  → 按序回收受阻
  → 8 个软件名额占满
  → 已发布的后续命令晚被 CPU 读取
```

这些比例只描述所采“末块发布→读取”区间，不能作为整个 Dispatch 的占比。软件名额 8 也不能当硬件 SQ 深度。[边界与 FIFO 重放](../reference_events/results/urma_boundaries_01_fifo_audit/ANALYSIS.zh-CN.md)

## 4. 从实现差异干预 FADD fence，首次得到完整调用收益

URMA 的 FADD 使用 STRONG，另设 fence；verbs native FADD 设置 SIGNALED，未设 IBV_SEND_FENCE。URMA 文档中 fence 约束前序 READ/atomic 与当前请求的发送，place_order 约束事务执行顺序。两后端完整语义仍应按各自接口判断。[URMA API 指南](https://docs.openeuler.org/zh/docs/24.03_LTS_SP3/unifiedbus/unifiedbus/urma/URMA%20API%20Guide.ch.html)

实验只关闭 **204 全部 Normal 数据 FADD** 的 fence，作用范围含 tail 通知和 head 消费反馈，包含 Normal Dispatch 和 Combine。保持 FADD STRONG、WRITE RELAX、窗口 8、completion all、lane-mixed，202 保持全开。关闭采集，A→B→B→A，每项预热 5 次、采样 10 次并丢首值。

| 配对 | 全开 A | 204 数据 fence 关闭 B | 节省 | 改善 |
| --- | ---: | ---: | ---: | ---: |
| A→B | 8.08223 ms | 7.81178 ms | 270.45 μs | 3.346% |
| B→A | 8.08491 ms | 7.80032 ms | 284.59 μs | 3.520% |
| 等权合并 | **8.08357 ms** | **7.80605 ms** | **277.52 μs** | **3.433%** |

相关最大轮内 CV 分别 0.511%／0.365%。两次 A 回到相近水平、两次 B 也接近，支持该环境下 fence 有部分净性能代价。主要改善在 202，204 本地合并均值仅缩短约 13.61 μs，符合跨端推进互相影响的结构。后续同 boot 的关闭采集控制再次得到 **8.07750→7.79617 ms，281.33 μs／3.483%**；该组没有重新反转顺序。[严格 ABBA](../reference_events/results/urma_fadd_fence_01_summary/ANALYSIS.zh-CN.md) · [后续控制](../reference_events/results/urma_fadd_fence_observe_02_AB_review_20261116/ANALYSIS.zh-CN.md)

这一阶段未得到 FP8 或 Combine 的一致收益。功能检查覆盖当时已跑形状，长期 slot 复用、更多节点及其他输入仍需验证。生产默认继续开 fence。

## 11. 把 fence 改动缩到 tail，寻找更小作用范围

`urma_fence_scope_01` 显式标注 Normal 的 2 处 tail、3 处 head 调用，测试 A 全开、B 仅 204 tail/head 都关、C 仅 204 tail 关，顺序 A→B→C→C→B→A。FADD 始终 STRONG，逐端源码、模块、boot 和关键参数一致，128 和正式正确性均通过。

| BF16 Dispatch | A 全开 | B 204 tail/head 都关 | C 204 只关 tail | C 相对 A |
| --- | ---: | ---: | ---: | ---: |
| 第 1 轮 | 9.058 ms | 8.817 ms | **7.828 ms** | 快 13.58% |
| 第 2 轮 | 8.234 ms | 7.825 ms | **7.813 ms** | 快 5.11% |

C 两次均值仅差 **15.39 μs（约0.20%）**。第二轮 C 与 B 差 12.43 μs，支持保留 tail-only 候选。A 两次差 824 μs，B 差 992 μs，两轮 C/B 均小于 1% 的预定门槛未通过。因此不把 13.58% 或 5.11% 当成已稳定确认的收益。FP8 和 Combine 未见一致改善。[三配置结果](../reference_events/results/urma_fence_scope_01_ANALYSIS.zh-CN.md)

## 12. tail-only 下继续拆返回和完成，确认剩余等待

`urma_fadd_tail_scope_01` 固定 BF16、最新 tail 角色实现和同模块，在 204 用密集 FADD 探针，202 用稀疏接收 GPU 事件。两配置各有前后关闭探针对照。六项双端任务通过，原始数据复算与上传的数值摘要一致。

| --- | ---: | ---: | ---: |
| pre | 8.27065 ms | **7.86463 ms** | 406.02 μs／4.91% |
| post | 8.86781 ms | **7.89168 ms** | 976.13 μs／11.01% |

tail-only 两控制均值只差 27.05 μs，202 轮内 CV 最高约 0.32%。全开控制漂移 **7.22%**；A/C 探针影响差为 **3.38 个百分点**，超过 1 个百分点门槛，整轮阶段归因未通过。204 本地两个配置各自的控制门槛通过，可以保留请求观测，跨配置的精确差值还可能受对端状态影响。

| 204 每配置 36 对的观测 | 全开 | 仅 tail 关 |
| --- | ---: | ---: |

## 13. 进入 provider 和 CQE 可见性层，当前结果与缺口

`urma_cqe_visibility_01` 仅在 204 读版本与能力，同上轮 boot，6 项 URMA 主库/common 文件名指纹均匹配。私有 `liburma-udma.so` SHA 为 `18ea061e…`，系统版为 `bcdf6f44…`，均保留 `udma_u_poll_jfc` 等符号。没有运行中 PID 的映射记录，当前只知道候选文件不同，尚不能声称历史 benchmark 混用 provider。

两处 tracefs 均返回 Permission denied，事件能力仍未知。匹配 SHA 的私有 SDK 定义了 JFC 的 CQE 地址、PI/CI 等可选字段，但 provider 是否实现合法查询、CQE 字段怎样解释仍需匹配版本的实现。该采集没有新增时延测量。[能力报告](results/urma_cqe_visibility_01/provider_probe_node1.json)

详细脚本 `6045db8f` 已在204执行，结果提交为 `ddcac8a6`。初始化和退出均成功，枚举6个设备，通过 `udmac0d1e2` 的 provider 回调地址解析到私有 `liburma-udma.so`，SHA仍为 `18ea061e…`，`matches_private=true`。反汇编、符号、section、动态链接及Build ID的五项采集均成功，SDK与上轮构建匹配。此次独立初始化验证了当前环境下所选设备的绑定，历史benchmark进程的实际provider仍需结合当时的加载环境判断。[实际设备选择](results/urma_cqe_visibility_02/node1/provider_select.log) · [采集清单](results/urma_cqe_visibility_02/node1/manifest.json)

目前已经有准确版本的轮询机器码可供离线审查。该步骤只初始化并枚举设备，没有创建通信上下文或测量完成时延，约350μs的最新等待读数仍来自上一轮。接下来可沿实机 `udma_u_poll_jfc` 核对owner判断、请求映射及JFC查询实现，再准备直接就绪观测。[下一步代码和操作文档](../urma_cqe_diag/README.zh-CN.md)

下一步要取得同一请求的 R、有效 CQE 可读、A 三点。用户态首次读到有效 CQE可给出就绪时间界限，精确的设备发布时间仍依赖设备 trace。若 CQE 早已可读却晚交付，再查共享 JFC 和 provider 队首规则；若 CQE 可读本身就晚，查设备完成条件和顺序依赖。当前还没有共享/独立 JFC 的性能 A/B 结果。
