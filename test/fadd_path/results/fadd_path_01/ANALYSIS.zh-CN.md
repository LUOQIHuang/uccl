## 2. 新分界在哪里

```text
W：本端SDK轮询返回WRITE完成
          ↓
R：本端CPU采样看到对应FADD返回缓冲区由0变为非0
          ↓
A：本端SDK轮询返回FADD完成
          ↓
H：CPU处理该条完成记录
```

R是本端返回值观测，不是远端GPU看见tail的时刻。其物理可见时刻只能用最后0/首次非0采样给界限；未在A前采到R的请求不补造分段数据。W/A是SDK轮询返回边界，与旧报告逐WR处理边界不同；本次又只选择ring0第6块，不能将与历史中位数的差异当作优化收益。

| 指标 | 202 | 204 |
| --- | ---: | ---: |
| W→A间隔中位数，36对/端 | 682.990 μs | 427.350 μs |
| A前已观测到R | 12/36 | 35/36 |
| 已见R后，仍至少有一次采样SDK空轮询 | 12/36 | 34/36 |
| R之后到A的保守下界，中位数 | 76.065 μs，12对 | 145.680 μs，35对 |

表中上下界分别对配对指标取中位数，并非一条真实请求的端点；不同子样本的中位数不能相加或相除作为整体占比。R之后的下界使用首次实际读到非0的时间，因此即使采样较粗，这段已经观测到的后续等待仍然存在。

### 返回后等待占比：逐请求计算后汇总

为避免中位数相除，定义每对请求的总间隔为G、返回后等待下界为L。有效子样本的汇总下界比例为ΣL/ΣG。全部36对的保守比例使用全部G作分母，未在CQE前观察到R的请求仅贡献0个“已证实的返回后等待”下界；这不表示其真实返回后等待为0。

| 节点 | 有效R配对数 | 有效子样本ΣL/ΣG | 有效子样本返回后比例上下界 | 全部36对已证实的返回后等待/总间隔 |
| --- | ---: | ---: | ---: | ---: |
| 202 | 12 | 1058.89/9372.56 = ≥11.30% | 11.30%～43.26% | 1058.89/25526.84 = ≥4.15% |
| 204 | 35 | 5701.30/16141.27 = ≥35.32% | 35.32%～85.58% | 5701.30/16423.36 = ≥34.71% |

各求和项单位为μs。上下界范围是采样时间界限，不是统计置信区间。这些是所采请求间隔的加权比例；请求存在重叠，ΣG不是整体Dispatch耗时。没有同口径verbs对照，不能将这些比例称为“URMA相对verbs多出的时间占比”。202覆盖不足，4.15%仅为保守证据下界，不说明202返回后链路比204快。

## 4. 结论与限制

1. 本轮再次观察到URMA WRITE→通知FADD完成观测之间的数百μs间隔。
2. 204有35/36对在FADD完成被SDK返回前已看到原子返回数据，34/36对在此后仍有采样空轮询。不能把整段等待都解释成“远端atomic还没执行”：至少一部分等待位于返回数据已本端可见之后。
3. SDK返回完成后逐WR的CPU处理偏移不到0.5μs，不是本次数百μs间隔的主要来源。该判断不等于整个Proxy没有问题，SDK返回之前的服务、队列和轮询仍在候选内。
4. 后续排查应聚焦返回后的完成交付、provider/SDK队列推进与CPU轮询服务，以及仍未拆开的返回前链路。现有观测不能进一步断言是物理CQE生成慢、provider阻塞、还是具体设备顺序依赖。
5. 202仅12/36对有有效R分界，不能用这个子样本代表全部202请求。204的证据覆盖更充分。
6. 本轮没有关闭任何顺序约束，也没有证明消除这段等待能使整体Dispatch减少同样的时长；Normal并行流水线仍需用整体关闭探针的优化对照验证。

## 5. 当前RDMA环境的下一步

优先运行已有[FADD专项文档](../../README.zh-CN.md)中的verbs后端，使用`BACKEND=verbs`，完成同一套prepare/build/check/run/collect，提供完整两端结果。不追加tokens扫描、LL或传输参数矩阵。

verbs返回scratch被不同请求复用，本轮不采R，不改原返回槽或SGE。仍可比较W→A、SDK调用/空返回次数、轮询服务检查点、SDK返回→CPU处理，先判断URMA特有长间隔是否伴随不同的本端轮询行为。旧verbs约4μs仅作历史参照，不代替这次同口径结果。

若同口径verbs仍显示短W→A而URMA返回后等待明显，下一步需要匹配实际运行版本的provider `poll_jfc`、CQE格式和原子返回处理实现，定位完成交付条件；不再重复同一局部观察实验期待自动区分硬件四段。
