每列独立取中位数。累计比例使用逐对后段下界之和除以同一批 W→A 总间隔之和。各请求在流水线中可重叠，这些累计值描述所采请求分布。204 的返回分界不确定窗口从旧稀疏采样的约 249.23 μs 降至 3.995 μs，旧的 34.71% 和本轮 59.77% 是不同轮次的证据下界。它们的变化不能解释为运行本身额外变慢。[逐对数据](summary_urma_dense/pairs.csv) · [旧采样分析](../fadd_path_01/ANALYSIS.zh-CN.md)

- **204 的主要候选已收窄到发送端完成交付。** 36/36 对在 FADD 完成返回前看到原子旧值，且之后都有空轮询。返回值已见后的空轮询中位数是 67 次（47–117 次）。后段最长单次调用的中位数为 0.080 μs，最长调用间隙的中位数为 6.600 μs，36 对里最大的单次间隙也只有 8.97 μs。SDK 返回该完成后，Proxy 处理记录仅约 0.18 μs（中位数）。因此「CPU 停了几百微秒没轮询」和「一次 SDK 调用卡了几百微秒」均与所采数据不符。
- **202 的主要等待在返回值可读前。** 该段占所采请求累计间隔至少 81.28%。返回后仍有 30/36 对经历空轮询，后段中位下界约 96.65 μs。返回前区间包含前序请求或顺序依赖、设备推进、远端访问和响应回写，当前时间戳只给出了合并区间。

本端读到 FADD 返回旧值与 SDK 交付完成是两个可区分的事件。204 在前一事件之后仍有数百微秒的等待，可以把接下来的核查集中到 **物理 CQE 何时发布，以及 provider 何时能按 CQ 顺序把它读出**。当前采样记录没有硬件 CQE 就绪时间，无法再将这两部分拆开。这些局部请求的等待对完整 Dispatch 的净影响仍要结合 GPU 消费和后续请求推进。
